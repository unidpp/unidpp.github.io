[[cl-events]]
== Event and lifecycle model

[[cl-event-model]]
=== Event model

Nothing shall ever be edited in place; every change after first
issuance shall be an appended, typed event (I4). Every event shall
carry:

* `seq` — its sequence number, starting at zero, strictly monotonic
 with no gaps;
* `occurredAt` — the occurrence time, a UTC timestamp per ISO 8601-1
 (local time is a presentation concern);
* `actorRole` and `actorId` — the appending role and actor identity;
* `eventType` — the event class (8.2);
* `payload` — the class-specific payload, structurally matching the
 event class;
* `trust` — the event's trust marker (11.2).

An event whose payload variant does not match its declared event class
shall be rejected (type agreement), and an event containing a status
change that is not a legal transition shall be rejected at construction
(8.4).

The canonical body of an event — the byte string that commitments hash
— shall be the deterministic serialization of the event value:
struct fields in declaration order, sorted maps, integer and string
scalars only.

Informative implementation reference: `crates/event/src/payload.rs`

[[cl-event-taxonomy]]
=== Event class taxonomy

The framework shall provide the sixteen lifecycle event classes — the
issuance class plus the fifteen post-sale classes E1 to E15 — listed in
Table 1, each with its default appending role.

[[tbl-event-taxonomy]]
.Table 1 — Lifecycle event classes (issuance and E1 to E15)
[cols="8,26,40,26",options="header"]
|===
| Class | Event | What changes | Default appending role

| E0 | `issuance` | passport creation; for derived passports, the input references (9.3) | issuing authority
| E1 | `custody.transfer` | custody link only (resale, lease, inheritance, liquidation) | custodian (+ counterparty)
| E2 | `part.replace` | old child reference marked removed, new child reference added, bill-of-materials instance updated | repairer
| E3 | `repair.perform` | repair record plus consumed parts (E2 within); authorization class: authorized, independent or do-it-yourself | repairer
| E4 | `product.modify` | instance facts; may spawn a derived type (E4b); mandatory profile re-evaluation | accredited modifier
| E5 | `software.update` | firmware and software version vector; capability enablement changes declared characteristics with no physical change; unlocked features listed | economic operator / service
| E6 | `upgrade.install` | new child reference | installer
| E7 | `refurbish.remanufacture` | condition grade; remanufacture may be a transformation event to a new type | refurbisher
| E8 | `consumable.replace` | child references, possibly regulated child passports | any, per profile
| E9 | `recall.campaign` | campaign reference plus recall predicate; downstream traversal plus custodian notification (7.7 e) | regulator / economic operator
| E10 | `correction` | new corrected fact plus reason; prior value preserved in the log | economic operator with attestation
| E11 | `status.change` | state-machine transition with authority check | regulator / economic operator per profile
| E12 | `flag.security` | security flag kind (theft or loss, or registered extension) plus reference (for example a police report as stamp); blacklist entry | authority + registry
| E13 | `decompose` | inverse transformation, 1 → N, to material passports | recycler (accredited for claims)
| E14 | `inspection.stamp` | lens-scoped attestation (11.3) | any verifier
| E15 | `milestone.record` | usage counters; edge-segment state commitment | device
|===

In addition to the sixteen lifecycle classes, the framework shall
provide the following auxiliary classes:

a) *transformation classes* — `split` (Clause 9), `combine` (Clause 9),
 `end-of-waste` (Clause 9);

b) *structural classes* — `install` and `uninstall` (7.6), with
 uninstall outcomes harvested, destroyed or reused;

c) *edge-visibility classes* — `edge.visibility.change` (a visibility
 transition on an existing edge) and `escrow.disclosure` (a
 disclosure ceremony executed on an escrowed or blind edge: court,
 regulator or consent), appended by the edge owner or trustee.

Event classes shall be identified by canonical tokens that are
case-insensitive and separator-insensitive at parse time and normalize
to the lowercase dotted forms of Table 1 (7.1 e).

[[cl-event-log]]
=== The append-only event log

The authoritative record of a subject shall be its event log: an
append-only, hash-chained sequence of sealed events (I4). The following
requirements apply.

a) *Chaining.* Each sealed event shall commit to the entire prefix: its
 commitment is `H(salt? ‖ prev ‖ canonicalBody)` over the previous
 sealed event's commitment (absent for the first event) and the
 event's canonical body, using SHA-256. Any in-place mutation of any
 historical event shall break chain verification.

b) *Sequence discipline.* Appends shall be strictly sequential with no
 gaps; an out-of-order or repeated sequence number shall be rejected.

c) *Salt discipline.* Where an event commitment is salted, the log
 shall record only an opaque salt reference (an index into the
 owner-side salt store), and no serialization of the log shall
 contain any salt. Salts shall be consumed at append time and dropped
 from working memory. A salted commitment shall at minimum be
 demonstrably distinct from the unsalted form of the same body.

d) *Anchoring.* Prefix truncation alone is not detectable from the
 chain; the log head shall therefore be verifiable against an
 externally witnessed transparency-log anchor. A log head that does
 not match the anchor is an anchor mismatch, and a prefix-consistent
 log that fails anchoring shall be treated as truncated or forked.
 Forks (diverging commitments for one identity) are integrity
 incidents and shall be adjudicated, never silently merged.

e) *Replay.* Current state shall be derived by replay: the current
 status, the safety flag, the current custodian and the correction
 and stamp counts shall be computable from the event sequence alone.
 The safety flag shall combine recall and security evidence with
 recall taking precedence: none, recall-active, security-flagged.

f) *Distributed authority.* No single party shall hold the
 authoritative record alone: each event is authored by its custodian
 at the time, registry holds identity and resolution, the current
 custodian holds the live twin segment, archives hold persistence,
 and consumer-held segments stay private (5.9). Anchoring is the
 globally consistent spine (seam S6).

====

(`EventLog`, `SealedEvent`, `SaltStore`) and
`crates/event/src/commitment.rs` (`event_commitment`).

[[cl-event-status]]
=== Status state machine

Passport status shall take one of the following normative values:
`issued`, `suspended`, `invalidated`, `non-conformant`, `consumed`,
`transformed`, `end-of-waste`, `archived` (I6). The legal transitions
are given in Table 2; all other transitions are illegal and shall be
rejected at event construction.

[[tbl-status-transitions]]
.Table 2 — Legal status transitions
[cols="30,70",options="header"]
|===
| From | To

| issued | suspended; invalidated; non-conformant; consumed; transformed; end-of-waste; archived
| suspended | issued (reinstate); invalidated; archived
| non-conformant | issued (re-evaluation pass); invalidated; archived
| end-of-waste | issued (re-entry as secondary raw material); archived
| consumed | archived
| transformed | archived
| invalidated | archived
|===

The following rules apply.

a) Suspension, invalidation and de-conformance proceed from `issued`;
 reinstatement proceeds from `suspended`; re-evaluation pass proceeds
 from `non-conformant`.

b) Transformation consumes inputs: the issuance and transformation
 machinery of Clause 9 transitions inputs to `consumed` or
 `transformed` — historical, still verifiable, still needed for
 as-of queries.

c) End-of-waste re-entry transitions `end-of-waste` to `issued`
 (9.4).

d) Every terminal path ends in `archived` (Tier C, 10.1); `archived`
 has no outgoing transitions; `invalidated`, `consumed` and
 `transformed` cannot return to `issued`.

e) Status example values published by other systems (for example the
 active/inactive/archived/invalid sets of the EU profile family)
 shall be mapped onto this state machine by profile adaptation, not
 by replacing it.

[NOTE]
====
Informative implementation reference: `crates/event/src/status.rs`
(`Status`, `can_transition`).
====

[[cl-event-rules]]
=== Corrections, re-evaluation and recalls

a) *Corrections never rewrite.* A correction shall append a new
 corrected fact with a reason, preserving the prior value in the log
 (event-sourcing); corrections shall never mutate historical events.

b) *Re-evaluation triggers.* Modifications (E4) and feature unlocks
 (E5) shall trigger profile re-evaluation (re-running the profile's
 bound rule packages, 9.6); status may go to `non-conformant pending
 re-evaluation`, with regulator notification per profile.

c) *Recalls traverse downstream.* Recall propagation shall traverse
 the provenance DAG downstream and notify custodians (9.1), using
 predicate-based recall (7.7 e): the campaign event carries the
 predicate; the recall set is never enumerated centrally.

d) *Carrier replacement* (physical code re-issue) is a registry event
 on unchanged identity (7.3 f).

e) *Post-sale extension.* Resellers, refurbishers and recyclers extend
 the event chain and never overwrite it; custody transfer is a signed
 ceremony (E1) so the trail survives multiple owners.

[[cl-event-asof]]
=== As-of queries and the two query modes

The framework shall provide two authoritative query modes; legal
purpose selects the mode (source invariant 7 of 5.11).

a) *Live view* — the current state, freshness-labelled (10.4).

b) *Notarized as-of snapshot* — the state reconstructed from the
 event-sourced record at a specified past time, log-anchored.

The following requirements apply.

c) The *as-of prefix* of a log at time T shall be the sequence of
 events that had occurred by T; the *state hash at T* shall be the
 head commitment of that prefix (empty before the first event).

d) Transformation events shall hash-link their inputs by as-of state
 hash (9.3), so that derived passports reference exactly the input
 states they consumed.

e) Profile-version bindings recorded as lifecycle events shall make
 manifest history as-of-reconstructable, answering "was this
 compliant when sold in a given year?".

f) Mirrors and caches shall always carry as-of stamps; because the
 projection is computed from the record, as-of queries shall be
 reproducible.

g) Notarized snapshots shall be anchored by log-anchored time-stamping
 (11.3, 11.6).
